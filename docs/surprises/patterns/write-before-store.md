kind: write-before-store
lesson: A run that writes before it stores its progress replays its writes when lost; store progress at each irreversible write. A stored state that waits on nobody needs a driver on load. A field the engine writes in play is seeded, then the world's (`SEEDED_THEN_OWNED`), or the next load reverts it.

---
**Mechanism:** A Combat Process stores its state only when its run ends, and the damage is written mid-run. Reloading the GM's client while the run waited on its windows lost the run and left the card at `react`; the next answer dealt the damage again (#249, live). An engine flaw, not a habit: tracked as #250. Writing the held rung before holding it (12f979b2) stopped the replay and left the Process at `injury` for good: nothing drove a stored state that waits on nobody (#250, pressed 2026-10-19). A stored state also has to survive the load itself: §46.4-BN found Bašmu's `boundToPlatformId`, written at the summons and reverted by the content sync, and Gilles (Caster) (#323) the same for `leavesWithSummoner`, so his outliving Elder Horrors left with his final defeat.
**Lesson:** Where a run writes and then waits, store how far it got right after the write, or stamp the write so a replay skips it. And a state stored mid-run that waits on nobody needs something to drive it on after a reload: storing it earlier turned the replay into a stall.
